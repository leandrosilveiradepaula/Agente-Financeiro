\## 6. Bloqueio externo conhecido — Watson Orchestrate



O n8n envia ao preflight somente:



```json

{

&#x20; "sql\_query": "<SQL encapsulada com LIMIT 0>"

}

```



A tool `sql\_query\_execute` do Watson Orchestrate acrescenta internamente um parâmetro `limit = 100`. O motor retorna:



```text

Invalid Input Error: Parameter argument/count mismatch,

identifiers of the excess parameters: limit, sql\_query

```



O usuário atual não possui permissão para alterar essa tool.



Classificação:



```text

origem: Watson Orchestrate

componente: sql\_query\_execute

categoria: contrato da tool / infraestrutura externa

reparável por Gemini: não

retry do mesmo payload: não resolve

```



O preflight não será removido, ignorado ou transformado artificialmente em aprovação.



\## 7. Benchmark 92



A SQL inicial continha referências inválidas:



```sql

ap.lucro\_bruto\_rs

ap.margem\_contribuicao\_rs

```



O repair substituiu corretamente essas referências por expressões calculadas. A aprovação final não ocorreu porque o preflight reparado foi bloqueado novamente pelo contrato da tool Watson.



A pergunta equivalente já havia sido validada em produção com retorno das quatro marcas.



\## 8. Critério de aceite desta fase



A separação operacional está consolidada porque:



\- os workflows possuem nomes explícitos de ambiente;

\- PROD e TEST estão publicados;

\- BENCHMARK aponta exclusivamente para TEST;

\- o export BENCHMARK está versionado;

\- o export TEST completo permanece local e fora do Git por conter credenciais;

\- a limitação do Watson está documentada;

\- nenhuma alteração experimental foi aplicada diretamente ao PROD.



Resultado oficial desta rodada:



```text

63 executados

62 aprovados

1 bloqueado por infraestrutura externa conhecida

0 regressões funcionais confirmadas

```



Não registrar como `63/63` ou `100%`.



\## 9. Processo para futuras evoluções



1\. Alterar somente o TEST.

2\. Executar benchmark pequeno.

3\. Executar benchmark completo.

4\. Separar falhas do agente, SQL, infraestrutura e bloqueios externos.

5\. Externalizar credenciais antes de versionar novos exports.

6\. Exportar e revisar os workflows.

7\. Abrir pull request.

8\. Promover para PROD somente após aprovação.

9\. Exportar o novo PROD.

10\. Criar tag após validação em produção.



\## 10. Regras de proteção



\- Não testar no PROD.

\- Não apontar BENCHMARK para PROD.

\- Não remover o preflight.

\- Não aplicar LIMIT SQL por padrão.

\- Não classificar erro de contrato Watson como reparável por Gemini.

\- Não adicionar ao Git exports que contenham credenciais literais.

\- Não usar `git add .` enquanto o export TEST sensível estiver no diretório.

\- Sempre conferir `git status` e `git diff --cached` antes do commit.
